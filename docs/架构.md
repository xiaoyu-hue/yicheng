# 一键成城 · 架构说明

这份文档记录一键成城的设计结构与不可破坏的纪律，供后续迭代时对照。项目规模小（三份源码、约 750 行），因此本文刻意保持轻量：只写已经落地的结构和真正约束实现的规则，不预设尚未出现的需求。

## 一、设计原则

1. **确定性优先**：种子进、图出，同种子必同图。这是产品的核心承诺，高于一切便利。
2. **零第三方依赖**：只用 Go 标准库。构建可复现、供应链无风险、单文件即可分发。
3. **一份核心，两个入口**：生成逻辑只写一遍，本地版与网页版共用，杜绝两端行为漂移。
4. **核心纯计算**：生成核心不碰网络、不碰文件、不碰全局状态，给定输入必得相同输出，可独立自检。

## 二、分层与依赖

```
入口层    main.go（本地服务/命令行）   wasm_main.go（浏览器）
              \                        /
渲染层         render.go（City → SVG 字符串）
                    ↑
核心层         city.go（种子 → City 数据结构）
```

| 层 | 文件 | 职责 | 不许做 |
|---|---|---|---|
| 核心层 | `city.go` | 撒点、泰森多边形、松弛、筑墙、选门、铺路、分坊、命名、散布屋顶、定河道，产出 `City` 结构体 | 不许输出 SVG、不许读时间、不许用全局随机源 |
| 渲染层 | `render.go` | 把 `City` 画成宣纸风 SVG：底图、纸纹、坊块、道路、文字 | 不许改动城的数据、不许引入新的随机决策（纸纹除外，见纪律 4） |
| 入口层 | `main.go` / `wasm_main.go` | 本地：HTTP 服务与命令行导出；网页：向页面暴露 `generateCity(种子, 规模)` | 不许包含任何生成逻辑，只做参数转换与调用 |

依赖方向单向向下：入口 → 渲染 → 核心的数据结构。页面（`web/index.html`、`docs/index.html`）只通过入口层调用，两份页面除调用方式外（本地版走 HTTP 接口、网页版直调 WebAssembly 函数）保持同一套交互。

两个入口互斥编译：`main.go` 带构建标签 `!(js && wasm)`，`wasm_main.go` 带 `js && wasm`，普通构建与网页构建各取其一。

## 三、确定性纪律

1. 核心层只使用显式构造的随机源 `rand.New(rand.NewSource(seed))`，禁止 `math/rand` 的全局函数与 `time` 包。
2. 凡迭代 `map` 后影响输出顺序之处，必须先把键排序再迭代（Go 的 map 迭代顺序是随机的，是确定性最常见的破坏者）。
3. 渲染层不参与生成决策；唯一例外是宣纸纸纹，它使用与种子无关的固定种子源，只影响底图噪点、不影响城本身。
4. 每次改动核心层，必须依次通过三道验证：
   - `go vet ./...` 无报错；
   - `go run . -check` 输出 OK（同种子连生成两遍，SHA-256 一致）；
   - 网页版与本地版对拍：本地导出 `go run . -seed 42 -out a.svg`，网页版在 Node 中加载 `docs/yicheng.wasm` 调 `generateCity("42","city")`，两份 SVG 的 SHA-256 必须一致。
5. 新增随机行为时，先问一句：它该由种子决定吗？只要答案是肯定的，就必须从核心的随机源取数，并写进 `-check` 的覆盖范围。

## 四、扩展指南

| 想加什么 | 动哪里 | 注意 |
|---|---|---|
| 新的坊种类 | `city.go` 的分坊规则 + 名字库；`render.go` 的坊种配色；《使用说明》的图例表 | 分坊规则按「先定功能坊、再填民居坊」的顺序写，新种类要明确自己的安置规则（按方位、按距城心远近或按距城门远近） |
| 新的规模 | `city.go` 的 `sizeSpecs` 加一项（环数与各环半径） | 半径是相对比例不是像素；加完跑三道验证，并目测三种旧规模无变化 |
| 新的城名 / 坊名 / 寺名 | `city.go` 的名字库常量 | 名字库只增不改顺序——洗牌抽名依赖顺序，改动顺序等于让旧种子全部变城（若有意为之，须升大版本并在提交说明中写明） |
| 新的地貌（如护城河、城外村落） | 核心层在 `City` 中加字段并生成，渲染层负责画 | 先定「由种子决定」的生成规则，再写渲染；不要只在渲染层贴装饰，那样两端容易漂移 |
| 新的主题（如水乡、边塞） | 优先参数化：把边界形状、河道走向、配色、名字库做成主题参数传给现有流水线 | 不要复制一份生成器改参数——两份生成器必然在后续迭代中分叉 |

## 五、已知限制

- 河流固定在城南，走向由正弦曲线决定，尚无穿城水道或多河汇流。
- 城墙形状由内圈坊的外缘决定，是「顺着坊界的折线墙」，不是几何正方形城墙。
- 图中文字使用观看设备的衬线字体渲染，不同设备上字体观感略有差异；核心版图与文字内容不受影响。
- WebAssembly 产物约 2.8 MB，首次加载耗时取决于网络；已通过浏览器缓存缓解，未做进一步瘦身（如改用 TinyGo），因为标准 Go 构建的跨端一致性更重要。

## 六、关键决策记录

| 决策 | 理由 |
|---|---|
| 水乡是山水的「加一步」而非第三份生成器（3.0 落地） | 水乡与山水共用 `generateOrganic`，只以开关多走运河一步：运河折线在派坊前算出、临水坊在派坊时就地转化、桥在渲染层用线段求交定位。旧格局输出逐字节不变（双格局哈希回归守住） |
| 主题（皮肤）只活在渲染层（2.1 落地） | 生成层只在 `City` 上记主题名，配色全部收进渲染层的色板表；默认主题与首版配色逐字节一致、用输出哈希回归守住——换皮肤永不换布局 |
| 格局以生成模式参数化（2.0 落地） | 棋盘格局只替换「切坊」一步（网格切坊＋城墙取直），派坊、屋舍、河流、渲染全部复用；禁止复制一份生成器改参数 |
| 城外景用独立派生随机源（2.0 落地） | 护城河由城界几何放大得到（无随机）；田垄与村落用种子派生的独立随机源生成，不占用主随机源的序列——山水格局旧种子的城内布局因此保持不变（已用种子 42 输出哈希回归验证） |
| 输出格式选 SVG 而非位图绘制 | 文字清晰、天然支持矢量下载与打印、字符串可哈希对拍验证确定性 |
| 网页版选 WebAssembly 而非服务器接口 | 生成是纯计算，放进浏览器后零服务器成本、可挂静态托管（GitHub Pages）、且与本地版共用同一份核心 |
| 页面保留本地版与网页版两份 | 两版调用方式不同（HTTP 接口 / 直调函数），强行合并会让其中一版背上无谓的适配层；交互与样式保持一致即可 |
| 坊界用泰森多边形而非方格 | 有机生长的古城感来自不规则坊界；方格棋盘是另一种城市形态（如唐长安），如要做应作为新主题参数化加入，而不是替换现有生成 |
